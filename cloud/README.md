# TempLearn Cloud

The Cloudflare Worker is the **authoritative TempLearn forecasting and learning engine**. Android is the user interface, local archive/cache and cloud client. The phone does not generate or train forecasts.

## Cloud engine

- `src/inference.ts`: the 62-feature temperature model, feature construction, base prediction and continuous verified-error correction.
- `src/trainer.ts`: the 250-epoch ridge-regression trainer, chronological 80/20 validation, 4,000-example sampling, local training and shared cross-location model.
- `src/index.ts`: historical bootstrap, observation ingestion, training orchestration, walk-forward replay, forecast vintages, live verification, dashboard/API and hourly scheduled execution.
- D1 stores hourly observations, local/shared model weights and validation statistics, imported legacy feedback, cloud-verified forecasts, replay state and issued forecast vintages.

The TypeScript engine is a port of the Android Kotlin implementation. It retains the 62 feature positions, normalisation, training constants, chronological split, geographic shared model, local prior regularisation, prediction correction and walk-forward verification. The cloud implementation should be treated as authoritative; the local Kotlin algorithms are retained in the repository during the migration for reference and regression checks, but are no longer called by the active sync or dashboard path.

## First launch and history migration

The initial Android sync downloads/imports the existing Open-Meteo historical archive into its private SQLite database, then transfers the canonical Best Match rows to D1 in ordered pages of 1,000. The transfer is resumable by timestamp, so an interrupted request or daily D1 quota limit does not restart the archive from the beginning.

Android also transfers its most recent 5,000 verified prediction-error samples. These are placed in a separate cloud feedback table and used to seed the cloud error-correction learner; new verification records generated by the cloud take precedence when they refer to the same target hour.

After the archive is uploaded, the Worker requests the most recent 96 hours from the same Open-Meteo Forecast API input source, using the selected location's coordinates and IANA timezone. It inserts only completed hourly values and uses the unique `(location_id, timestamp_sec)` key with `INSERT OR IGNORE`. Therefore, hours already transferred from the historical archive or existing local recent data are not duplicated. Only missing timestamps from the 96-hour window are added.

The request uses the 15 hourly fields already used by TempLearn:

```
temperature_2m,relative_humidity_2m,dew_point_2m,precipitation,rain,
snowfall,weather_code,cloud_cover,cloud_cover_low,cloud_cover_mid,
cloud_cover_high,pressure_msl,wind_speed_10m,wind_gusts_10m,
shortwave_radiation
```

It sets `past_hours=96`, `forecast_hours=0`, `timeformat=unixtime`, temperature in Celsius, wind in km/h, precipitation in mm and `models=best_match`. Future provider temperature forecasts are not used as prediction inputs. The source values are Open-Meteo Best Match model-derived past-hour estimates, not direct thermometer observations.

When the initial history and feedback migration complete, the Worker trains the local model and the shared model, runs walk-forward replay for the recent completed period, reconciles saved cloud forecast vintages against later input data and generates the next-hour TempLearn prediction.

## Ongoing operation

The Worker runs hourly from its Cron Trigger:

1. Retrieves the latest 96 completed past hours for each bootstrapped location.
2. Inserts only new timestamps and leaves previously stored rows untouched.
3. Verifies cloud forecast vintages whose target timestamp now has a completed input record.
4. Re-trains local/shared models when new observations arrive.
5. Performs walk-forward replay with feedback limited to targets that occurred before each replay prediction.
6. Generates and stores the next-hour TempLearn forecast.

Android downloads the cloud dashboard and forecast, caches model statistics and recent observations for the UI, and displays cached cloud forecasts. Reopening the app retrieves the latest cloud state. The cloud continues operating when the phone is offline.

## Cloudflare configuration

Keep the Cloudflare project root directory at `cloud`:

- Build command: `npm install`
- Deploy command: `npx wrangler deploy`
- Preview command: `npx wrangler dev`

The existing D1 binding and database are configured in `wrangler.toml`. The Worker creates its operational tables and adds missing columns automatically; it does not drop the existing forecast-vintage table or its data.

### Required secret

Create a Worker secret called `SYNC_KEY` in **Workers & Pages → templearn-cloud → Settings → Variables and Secrets**. Add the same value to the repository's GitHub Actions secrets as `TEMPLEARN_CLOUD_SYNC_KEY`. Add the actual Worker base URL as `TEMPLEARN_CLOUD_BASE_URL`. Never commit either value to source control.

The current prototype embeds the sync key in the APK, which makes it extractable. This is acceptable only as a personal-use gate; public distribution would require per-device authentication rather than a shared APK key.

## API

- `GET /health` — service and engine status.
- `GET /v1/bootstrap/status?locationId=...` — resumable initial-history status.
- `POST /v1/bootstrap/start` — start or resume transfer for a location.
- `POST /v1/bootstrap/batch` — upload up to 1,500 ordered observations.
- `POST /v1/bootstrap/feedback/batch` — upload up to 1,500 ordered legacy verified-error samples.
- `POST /v1/bootstrap/feedback/complete` — finish legacy feedback transfer.
- `POST /v1/bootstrap/complete` — close initial transfer and train/run the cloud engine.
- `POST /v1/sync` — retrieve new 96-hour input data, learn, verify and forecast.
- `GET /v1/dashboard?locationId=...` — cached model, recent observations, latest cloud forecast and counts.
- `GET /v1/forecasts?locationId=...&from=...&to=...` — stored forecast vintages.

All `/v1/*` endpoints other than the read-only forecast-vintage endpoint require the `x-templearn-key` header. The forecast-vintage endpoint is read-only and exposes predictions only.

## Runtime plan

This workload is heavier than a simple API proxy: initial transfer writes hundreds of thousands of observation rows, and the trainer executes 250 epochs over up to 4,000 examples per location. Cloudflare Workers Free has a 10 ms CPU limit, which is not sufficient for this historical training workload. `wrangler.toml` therefore sets `limits.cpu_ms = 300000` (5 minutes), which requires **Workers Paid**. The code also reuses the local fit as the shared fit when only one location is bootstrapped, avoiding duplicate computation. D1 daily write quotas still apply; the resumable transfer allows upload to continue across quota windows.
